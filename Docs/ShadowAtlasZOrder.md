# 그림자 아틀라스와 Z-order 인덱스

> 이 문서는 [ShadowAtlasAllocator.cpp](../Source/Runtime/Render/ShadowAtlasAllocator.cpp)가 왜 타일 위치를 **Z-order(모턴 코드, Morton code)** 라는 숫자로 표현하는지 쉽게 설명합니다.

---

## 1. 먼저, 우리가 풀려는 문제

그림자 아틀라스는 **8192 × 8192 크기의 큰 도화지 한 장**입니다.
여러 조명(Point Light, Spot Light)이 이 도화지를 나눠 쓰면서 각자 자기 그림자를 그립니다.

도화지는 이렇게 나눕니다.

- 도화지를 **4등분** 하면 4096 크기 칸 4개
- 그 칸 하나를 또 4등분 하면 2048 크기 칸 4개
- … 이렇게 계속 나눠서 가장 작은 칸은 **256 크기**

이렇게 "4개로 쪼개고, 또 4개로 쪼개는" 구조를 **쿼드트리(Quadtree)** 라고 합니다.

```
┌───────┬───────┐        ┌───┬───┬───────┐
│       │       │        │   │   │       │
│   0   │   1   │        ├───┼───┤   1   │
│       │       │   →    │   │   │       │
├───────┼───────┤        ├───┴───┼───────┤
│       │       │        │       │       │
│   2   │   3   │        │   2   │   3   │
│       │       │        │       │       │
└───────┴───────┘        └───────┴───────┘
  한 번 쪼갠 모습          0번 칸을 한 번 더 쪼갠 모습
```

이때 프로그램은 각 칸에 대해 이런 질문에 빠르게 답할 수 있어야 합니다.

1. 이 칸은 도화지의 **어디(x, y)** 에 있지?
2. 이 칸의 **부모**(나를 품고 있는 큰 칸)는 누구지?
3. 이 칸의 **형제**(같이 쪼개진 나머지 3칸)는 누구지?
4. 빈 칸이 여러 개면 **어떤 칸부터** 쓰지?

이 질문들에 답하려면 칸마다 **이름(번호)** 을 붙여야 합니다.
어떤 방식으로 번호를 붙이느냐가 바로 이 문서의 주제입니다.

---

## 2. 평범한 번호 붙이기: 줄 단위(Row-major)

가장 먼저 떠오르는 방법은 책 읽듯이 **왼쪽 → 오른쪽, 위 → 아래** 로 번호를 매기는 것입니다.
4 × 4 칸으로 예를 들어 볼게요.

```
 x →  0   1   2   3
y ┌───┬───┬───┬───┐
0 │ 0 │ 1 │ 2 │ 3 │
  ├───┼───┼───┼───┤
1 │ 4 │ 5 │ 6 │ 7 │
  ├───┼───┼───┼───┤
2 │ 8 │ 9 │10 │11 │
  ├───┼───┼───┼───┤
3 │12 │13 │14 │15 │
  └───┴───┴───┴───┘
```

여기서 **왼쪽 위 큰 칸(2 × 2)** 에 들어 있는 번호를 보면 `0, 1, 4, 5` 입니다.
번호가 **띄엄띄엄** 떨어져 있죠. 그래서

- "큰 칸 하나 = 번호 몇 번부터 몇 번까지" 라고 말할 수 없고,
- 부모나 형제를 찾으려면 결국 x, y로 다시 바꿔서 계산해야 합니다.

쿼드트리와 궁합이 좋지 않습니다.

## 3. Z-order 번호 붙이기

Z-order는 **"큰 칸 안의 작은 칸들은 항상 붙어 있는 번호를 갖게"** 번호를 매기는 방법입니다.
규칙은 딱 하나입니다.

> 어떤 칸이든 4등분 했을 때 순서는 항상
> **왼쪽 위(0) → 오른쪽 위(1) → 왼쪽 아래(2) → 오른쪽 아래(3)**

이 순서로 선을 그어 보면 알파벳 **Z** 모양이 됩니다. 그래서 이름이 Z-order입니다.

```
  0 ──→ 1
       ╱
      ╱
  2 ──→ 3
```

이 규칙을 큰 칸에도, 그 안의 작은 칸에도 똑같이 적용하면 4 × 4 칸은 이렇게 됩니다.

```
 x →  0   1   2   3
y ┌───┬───┬───┬───┐
0 │ 0 │ 1 │ 4 │ 5 │
  ├───┼───┼───┼───┤
1 │ 2 │ 3 │ 6 │ 7 │
  ├───┼───┼───┼───┤
2 │ 8 │ 9 │12 │13 │
  ├───┼───┼───┼───┤
3 │10 │11 │14 │15 │
  └───┴───┴───┴───┘
```

이제 큰 칸(2 × 2)들을 보세요.

| 큰 칸 | 들어 있는 번호 |
|---|---|
| 왼쪽 위 | 0, 1, 2, 3 |
| 오른쪽 위 | 4, 5, 6, 7 |
| 왼쪽 아래 | 8, 9, 10, 11 |
| 오른쪽 아래 | 12, 13, 14, 15 |

**번호가 전부 연속**입니다! 그래서 큰 칸 하나를 **"시작 번호 + 개수"** 로 부를 수 있습니다.

### 예시로 확인하기: "4번부터 4개"

"4번부터 4개" 라고 말하면 `4, 5, 6, 7` 번 작은 칸을 뜻합니다.
위 Z-order 표에서 찾아보면 이 네 칸은 정확히 **오른쪽 위 2 × 2 큰 칸** 을 이룹니다.

```
 x →  0   1   2   3
y ┌───┬───┬───┬───┐
0 │   │   │ 4 │ 5 │   ← "4번부터 4개"
  ├───┼───┼───┼───┤      = 오른쪽 위 큰 칸
1 │   │   │ 6 │ 7 │
  ├───┼───┼───┼───┤
2 │   │   │   │   │
  ├───┼───┼───┼───┤
3 │   │   │   │   │
  └───┴───┴───┴───┘
```

몇 가지 더 해 보면:

| 이렇게 부르면 | 해당 번호 | 실제 모양 |
|---|---|---|
| 0번부터 16개 | 0 ~ 15 | 도화지 전체 |
| 8번부터 4개 | 8, 9, 10, 11 | 왼쪽 아래 2 × 2 큰 칸 |
| 12번부터 4개 | 12, 13, 14, 15 | 오른쪽 아래 2 × 2 큰 칸 |
| 9번부터 1개 | 9 | 작은 칸 하나 (x=1, y=2) |

같은 걸 **줄 단위 번호(2장의 표)** 로 해 보면 망가집니다.
오른쪽 위 큰 칸은 줄 단위로 `2, 3, 6, 7` 인데, "2번부터 4개" 라고 하면 `2, 3, 4, 5` 가 되어 **엉뚱한 칸** 을 가리킵니다.
줄 단위에서는 큰 칸을 표현하려면 결국 "x는 2~3, y는 0~1" 처럼 좌표 범위를 따로 들고 다녀야 합니다.

### "개수"는 따로 저장 안 해도 된다

"개수" 는 칸의 **크기(Level)** 만 알면 정해집니다. (2 × 2 큰 칸이면 항상 4개)
그리고 할당기는 빈 칸 목록을 **Level별로 따로** 가지고 있습니다 (`FreeLists[Level]`).

예를 들어 4 × 4 도화지에서 작은 칸 하나(0번)를 할당하고 나면:

```
FreeLists[1] = [ 4, 8, 12 ]   ← "2 × 2 크기 빈 칸: 4번부터, 8번부터, 12번부터"
FreeLists[2] = [ 1, 2, 3 ]    ← "1 × 1 크기 빈 칸: 1번, 2번, 3번"
```

어느 목록에 들어 있느냐가 이미 크기를 알려 주므로, 목록 안에는 **시작 번호 숫자 하나만** 넣으면 됩니다.

## 4. Z-order 번호는 사실 "주소"다

Z-order 번호를 **4진법**으로 바꿔 보면 재미있는 일이 생깁니다.
4진법 각 자리가 "몇 번 칸으로 들어가라" 는 **길 안내**가 됩니다.

예를 들어 번호 `9`를 4진법으로 쓰면 `21` 입니다.

```
9  =  4진법 "2 1"
             │ └─ 그 안에서 1번(오른쪽 위) 칸으로
             └─── 먼저 2번(왼쪽 아래) 큰 칸으로
```

위 표에서 확인해 보면, 왼쪽 아래 큰 칸 `{8, 9, 10, 11}` 안에서 오른쪽 위가 정말로 `9` 입니다.

우편 주소랑 똑같습니다.

> **서울시** → **강남구** → **역삼동** → **123번지**

큰 지역부터 작은 지역으로 내려가는 것처럼, Z-order 번호도 **앞자리일수록 큰 칸, 뒷자리일수록 작은 칸** 을 가리킵니다.
그래서 번호 하나만 보고도 "쿼드트리의 어느 가지에 있는지" 를 알 수 있습니다.

## 5. 번호에서 x, y 꺼내기 (비트 끼워 넣기)

컴퓨터는 2진법을 쓰니까 2진법으로 보면 더 간단합니다.
Z-order 번호는 **x의 비트와 y의 비트를 번갈아 끼워 넣은 것**입니다.

```
번호의 비트 :   y1  x1  y0  x0
```

예시: `x = 1`, `y = 2` 인 칸

```
x = 1  →  x1 = 0, x0 = 1
y = 2  →  y1 = 1, y0 = 0

번호 =  y1 x1 y0 x0
     =   1  0  0  1   (2진법)
     =   9            (10진법)
```

표에서 (x=1, y=2) 위치가 정말 `9` 입니다.

거꾸로, 번호에서 x를 꺼내려면 **짝수 번째 비트만** 골라 모으면 되고, y는 한 칸 밀어서(`>> 1`) 똑같이 하면 됩니다.
코드의 `CompactEvenBits` 가 바로 이 일을 합니다.

```cpp
FShadowAtlasTile FShadowAtlasAllocator::MakeTile(uint32 Index, uint32 Size) const
{
	const uint32 CellX = CompactEvenBits(Index);       // 짝수 번째 비트 → x
	const uint32 CellY = CompactEvenBits(Index >> 1);  // 홀수 번째 비트 → y
	const uint32 PixelX = CellX * MinTileSize;
	const uint32 PixelY = CellY * MinTileSize;
	...
}
```

## 6. 실제 코드에서 Z-order가 해 주는 일

실제 아틀라스는 가장 작은 칸이 256이므로 `8192 / 256 = 32`, 즉 **32 × 32 = 1024 칸**입니다.
각 단계(Level)의 칸이 차지하는 작은 칸 개수는 다음과 같습니다.

| Level | 칸 크기 | 차지하는 작은 칸 수 `CellsAt(Level)` |
|---|---|---|
| 0 | 8192 | 1024 |
| 1 | 4096 | 256 |
| 2 | 2048 | 64 |
| 3 | 1024 | 16 |
| 4 | 512 | 4 |
| 5 | 256 | 1 |

Z-order 덕분에 1장에서 던졌던 질문들이 전부 **덧셈 / 비트 연산 한 줄** 로 끝납니다.

### ① 이 칸은 어디 있지?
→ 5장처럼 비트를 나눠 꺼내면 끝 (`MakeTile`). **Level을 몰라도 됩니다.**
큰 칸의 번호 = 그 칸 왼쪽 위 작은 칸의 번호이기 때문입니다.

#### 예시로 확인하기: 같은 번호, 다른 크기

4 × 4 표에서 번호 `8` 을 생각해 봅시다. `8` 은 두 가지 칸의 시작 번호가 될 수 있습니다.

```
 크기 1 × 1 로 보면          크기 2 × 2 로 보면
 ┌───┬───┬───┬───┐          ┌───┬───┬───┬───┐
 │   │   │   │   │          │   │   │   │   │
 ├───┼───┼───┼───┤          ├───┼───┼───┼───┤
 │   │   │   │   │          │   │   │   │   │
 ├───┼───┼───┼───┤          ├───┴───┼───┼───┤
 │ 8 │   │   │   │          │       │   │   │
 ├───┼───┼───┼───┤          │   8   ├───┼───┤
 │   │   │   │   │          │       │   │   │
 └───┴───┴───┴───┘          └───────┴───┴───┘
  8번 작은 칸 하나            8번부터 4개 (8, 9, 10, 11)
```

두 경우 모두 **왼쪽 위 모서리는 (x=0, y=2)** 로 똑같습니다.
그리고 `8` 을 비트로 풀어 보면 (2진법 `1000` → y1=1, x1=0, y0=0, x0=0) 정말 **x=0, y=2** 가 나옵니다.

즉, 번호를 풀어서 나오는 (x, y) 는 **"그 칸이 몇 칸짜리든 상관없이 왼쪽 위 모서리"** 입니다.
그래서 위치를 구할 때 Level은 필요 없고, **크기(Size)는 "어디까지 뻗어 있는지"** 를 알려 줄 때만 필요합니다.

한 번 더 해 볼게요. 번호 `0` 은

- 도화지 전체(16개)의 시작
- 왼쪽 위 2 × 2 큰 칸(4개)의 시작
- 왼쪽 위 작은 칸(1개)

모두 같은 번호 `0`, 같은 모서리 (0, 0) 입니다.

왜 이렇게 될까요? 큰 칸을 쪼개면 **0번 자식은 항상 "부모 번호 + 0 × 크기 = 부모 번호"** 이기 때문입니다.
그래서 부모 → 0번 자식 → 그 0번 자식 … 으로 아무리 내려가도 번호가 바뀌지 않고, 모서리도 바뀌지 않습니다.

#### 실제 아틀라스 예시

번호 `256` 을 풀어 봅시다. 2진법으로 `1 0000 0000`, 0부터 셌을 때 8번 비트(짝수 → x 쪽)만 1입니다.

- `CompactEvenBits(256)` = 16 → CellX = 16 → PixelX = 16 × 256 = **4096**
- `CompactEvenBits(256 >> 1)` = 0 → CellY = 0 → PixelY = **0**

그러니 `256` 은 크기가 무엇이든 **(4096, 0)**, 즉 오른쪽 위 4096 칸의 모서리에서 시작합니다.

| 번호 | 크기 | 차지하는 작은 칸 번호 | 픽셀 영역 |
|---|---|---|---|
| 256 | 4096 | 256 ~ 511 (256개) | (4096, 0) ~ (8192, 4096) |
| 256 | 2048 | 256 ~ 319 (64개) | (4096, 0) ~ (6144, 2048) |
| 256 | 256 | 256 (1개) | (4096, 0) ~ (4352, 256) |

#### 비교: 힙(Heap) 방식이었다면?

힙 방식은 노드마다 번호가 따로 붙습니다 (루트 0, 그 자식 1 ~ 4, 손자 5 ~ 20 …).
도화지 왼쪽 위 모서리 하나에 대해서도 Level마다 번호가 다릅니다: 전체 = `0`, 큰 칸 = `1`, 그 안의 작은 칸 = `5` …
그래서 번호만 봐서는 위치를 알 수 없고, **"이 번호가 몇 번째 Level인지"** 를 먼저 알아야 위치를 계산할 수 있습니다.

### ② 자식(4개로 쪼갠 칸)은 누구지?
번호가 연속이니까 그냥 더하면 됩니다.

```
자식 c번 = 내 번호 + c × (자식 하나의 크기)
```

예: Level 1의 1번 칸(번호 `256`)을 쪼개면 자식 크기는 `64` 이므로
→ `256`, `320`, `384`, `448`

```cpp
// Allocate(): 큰 칸을 쪼개서 나머지 3개를 빈 칸 목록에 넣기
uint32 Child = CellsAt(Level + 1);
for (uint32 i = 1; i <= 3; ++i)
	FreeLists[Level + 1].Add(Index + i * Child);
```

### ③ 부모는 누구지?
4진법 주소의 **마지막 자리를 0으로 지우면** 부모입니다. 비트로는 아래쪽 비트를 지우는 것과 같습니다.

```cpp
// Free(): 부모 번호 구하기
const uint32 Parent = Index & ~(CellsAt(Level - 1) - 1);
```

예: `320 & ~(256 - 1)` = `256` → 320번 칸의 부모는 256번 칸

### ④ 이 번호가 이 크기의 칸으로 올바른가?
올바른 칸이라면 번호가 칸 크기로 **나누어 떨어져야** 합니다.

```cpp
assert(Index % CellsAt(Level) == 0);
```

### ⑤ 빈 칸이 여러 개면 어디부터 쓰지?
그냥 **번호가 가장 작은 칸** 부터 씁니다 (`PopLowest`).
Z-order에서는 작은 번호 = 왼쪽 위 큰 칸부터 차례로 채워지기 때문에,
조각이 여기저기 흩어지지 않고 **한쪽부터 빽빽하게** 채워집니다.

## 7. 그런데 `FShadowAtlasTile` 에는 왜 X, Y가 있을까?

```cpp
struct FShadowAtlasTile
{
	uint32 X = 0;      // 픽셀 좌표 (Index에서 계산한 값)
	uint32 Y = 0;
	uint32 Size = 0;
	uint32 Index = 0;  // Z-order 번호 (진짜 기준)
};
```

"번호 하나면 된다더니 X, Y는 왜 또 저장하지?" 라는 의문이 들 수 있습니다.
답은 **누가 쓰느냐** 에 따라 필요한 게 다르기 때문입니다.

### 할당기 안에서는 → `Index` 만 쓴다

- 빈 칸 목록 `FreeLists` 에는 `uint32` 번호만 들어 있습니다.
- 쪼개기, 형제 찾기, 합치기, `PopLowest` 모두 `Index` 만 가지고 계산합니다.
- `Free(Tile)` 도 `Tile.Index` 와 `Tile.Size` 만 읽고, **X, Y는 보지 않습니다.**

"숫자 하나로 충분하다" 는 장점은 바로 **이 내부 관리** 에 대한 이야기입니다.

### 할당기 밖(렌더러)에서는 → 픽셀 좌표가 필요하다

렌더러는 쿼드트리에 관심이 없고, 그냥 **"도화지 어디에 그리면 돼?"** 만 알고 싶습니다.

- `RenderLocalAtlas` 는 `SetViewport(Tile.X, Tile.Y, Tile.Size, Tile.Size)` 로 그릴 영역을 정합니다.
- `TileToAtlasRect` 는 `X / AtlasSize`, `Y / AtlasSize` 로 셰이더에 넘길 UV 영역을 만듭니다.

그래서 할당기는 타일을 내줄 때 (`MakeTile`) **번호를 픽셀 좌표로 한 번 풀어서 같이 적어 줍니다.**
덕분에 렌더러는 Z-order, `CompactEvenBits`, `MinTileSize` 같은 걸 전혀 몰라도 됩니다.

### 정리

| 필드 | 역할 | 누가 쓰나 |
|---|---|---|
| `Index` | **진짜 기준**. 쿼드트리 안에서 이 칸이 누구인지 | 할당기 (`Free`) |
| `Size` | 칸 크기 (→ `LevelOf` 로 Level 계산) | 할당기, 렌더러 |
| `X`, `Y` | `Index` 에서 **계산해서 저장해 둔 값** (편의용 캐시) | 렌더러, 셰이더 설정 |

X, Y는 할당 로직에 전혀 쓰이지 않습니다. 없애도 동작은 같지만, 그러면 쓰는 곳마다 `Index` 를 풀어야 합니다.
타일 하나당 8바이트를 더 써서 사용하는 코드를 단순하게 만든 선택입니다.

## 8. 다른 방법들과 비교

Z-order만 쿼드트리를 표현할 수 있는 건 아닙니다. 다른 방법도 있습니다.

| 방법 | 어떻게? | 장점 | 단점 |
|---|---|---|---|
| **Z-order (현재 방식)** | x, y 비트를 번갈아 끼운 숫자 하나 | 숫자 하나로 위치 + 트리 위치를 동시에 표현, 부모·자식·형제 계산이 한 줄 | 처음 보면 낯설다 (비트 끼워 넣기) |
| **(x, y) 좌표 + 크기** | 픽셀 좌표를 그대로 저장 | 읽기 쉽고 직관적 | 숫자를 2개씩 들고 다녀야 하고, "가장 작은 칸" 기준을 따로 정해야 함 |
| **힙(Heap) 방식 노드 번호** | 루트 0, i번의 자식은 4i+1 ~ 4i+4 | 모든 노드 상태를 배열/비트맵 하나로 관리하기 좋음 | 번호만으로 위치를 알 수 없음, Level에 따라 계산식이 달라짐 |
| **포인터로 연결된 트리** | 노드 객체가 자식 4개를 가리킴 | 아주 유연함 | 메모리 할당, 포인터 따라가기 → 이 정도 일에는 너무 무거움 |
| **줄 단위 번호 (Row-major)** | y × 32 + x | 단순함 | 큰 칸 안의 번호가 연속이 아니라서 쿼드트리 계산에 도움이 안 됨 |

### 그래서 왜 Z-order를 골랐나?

1. **할당기 내부에서는 숫자 하나로 충분하다.** 빈 칸 목록(`FreeLists`)이 그냥 `uint32` 배열이면 됩니다. (밖으로 내주는 타일에는 렌더러 편의를 위해 X, Y를 같이 적어 줍니다 — 7장 참고)
2. **계산이 덧셈과 비트 연산뿐이다.** 부모, 자식, 형제, 정렬 확인이 모두 한 줄입니다.
3. **Level을 몰라도 위치를 알 수 있다.** 큰 칸 번호 = 그 칸 왼쪽 위 작은 칸 번호이기 때문입니다.
4. **작은 번호부터 쓰면 자연스럽게 빽빽하게 채워진다.** 조각화(빈 틈이 여기저기 생기는 현상)가 줄어듭니다.

`(x, y)` 좌표 방식으로 만들어도 **똑같이 동작**합니다. Z-order는 "꼭 필요해서" 라기보다,
**"위치"와 "트리에서의 위치"를 숫자 하나에 담아 코드를 짧고 단순하게 만들어 주기 때문에** 선택한 방법입니다.

---

## 한 줄 요약

> Z-order는 칸을 항상 **Z 모양(왼위 → 오위 → 왼아래 → 오아래)** 순서로 번호 매기는 방법이다.
> 이렇게 하면 **큰 칸 안의 번호가 연속**이 되고, 번호 하나가 곧 **쿼드트리 주소**가 되어
> 부모·자식·위치 계산이 전부 간단한 산수로 끝난다.
